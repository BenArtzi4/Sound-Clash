# Observability — I-Vitals (T1.7)

The Grafana layer on top of the Faro telemetry that went live on 2026-07-12
(PR #258). Three output channels, all built and validated against **real
production data** from `https://www.soundclash.org`:

1. **Display** — the `Sound Clash - Vitals` Grafana dashboard.
2. **Push (email)** — a native Grafana Cloud email alert for the systemic #254
   signal, to `benartzi4@gmail.com`.
3. **Push (GitHub)** — a scheduled Action that files one GitHub issue per #254
   incident.

Everything here is applied **by the maintainer**: the Grafana MCP in this repo
is read-only (`-disable-write`, Viewer token), so this directory ships
importable JSON/YAML + click-by-click steps rather than writing to Grafana
directly.

## Stack & datasources

- Grafana Cloud: `https://prudentcurrant2518.grafana.net`
- `grafanacloud-logs` (Loki) — Faro logs/events/measurements
- `grafanacloud-traces` (Tempo) — Faro custom spans
- `grafanacloud-prom` (Prometheus) — currently only `grafanacloud_feo11y_app_info`
  (see [supabase-metrics-scrape.md](supabase-metrics-scrape.md))

### Faro data shape (what the queries rely on)

Faro tags every signal `service_name="sound-clash-web"`,
`deployment_environment="production"`. Stream labels are only `kind`
(`event` / `log` / `measurement` / `exception`), `detected_level`,
`service_name`. **Loki lines are logfmt, not JSON** — everything else needs
`| logfmt`. App context keys are prefixed `context_`, Faro event data
`event_data_`.

| Signal | kind | Key fields (after `| logfmt`) |
|---|---|---|
| `stale_buzz_lock_resynced` (warn) | log | `context_game_code`, `context_stale_team`, `context_fresh_team`, `session_id`, `page_id` |
| `realtime_disconnect` (warn) | log | `context_game_code`, `context_sub_status` |
| `yt_preload_retry`, `yt_preload_not_ready` (warn) | log | Retired 2026-10-31 with the host's hidden standby player (YouTube's embed rules allow no hidden player that plays). Older lines are the standby's: a retried prebuffer, a dead standby skipped at Next round |
| `yt_preload_error` (warn) | log | Read by the weekly dead-video scan. Since 2026-10-31: the host's one player had loaded nothing 10 s after a song's load and issued it again (`context_code=no_bytes`, `context_stall=no_bytes`, plus `context_game_code`, `context_youtube_id`, `context_url`, `context_song_id`, `context_title`, `context_artist`). Before that: a YouTube error on the hidden standby (`context_code` = YouTube's error code, same song fields) |
| `yt_live_stall` (warn) | log | `context_kind=no_start`: the song had not reached PLAYING 10 s after its load and was not paused by the app meanwhile (`context_state`, `context_loaded_fraction`). `context_retried=true`: it had loaded nothing, so the player issued the load once more (since 2026-10-31); `false`: it had bytes and was left alone, or it was the retry. `context_kind=early_pause`: it paused by itself within 5 s of starting (`context_ms_after_start`), telemetry only. Both carry `context_game_code` and the song fields (`context_player` until 2026-10-31) |
| `realtime_fanout` | event | `event_data_event_type` (game/team/round), `event_data_fanout_ms` |
| `landing` | event | `event_data_view`, `event_data_ref_host`, `event_data_ref`, `event_data_src`, `event_data_utm_*`. One per page load: where the visit came from |
| `view` | event | `event_data_view` (route template). One per route reached |
| `cta` | event | `event_data_id` (`home_host`, `landing_host`, `setlist_share`, ...) |
| `team_joined` | event | `event_data_source` (`qr` / `link` / `typed`) |
| `game_created` | event | `event_data_genres_count`, `event_data_decades_count`, `event_data_returning` |
| web-vitals | measurement | `type="web-vitals"`, `lcp` / `inp` / `fcp` / `ttfb`, `context_rating` |
| Tempo spans | — | `game.buzz.e2e` (`outcome`, `realtime.fanout_ms`), `game.score.e2e`, `game.song_start` (`preloaded`, always false since the standby went on 2026-10-31), `db.rpc` (`rpc.name`), `game.player_init` |

## 1. Dashboard — `Sound Clash - Vitals`

- File: [`dashboards/sound-clash-vitals.json`](dashboards/sound-clash-vitals.json)
  (generated by [`dashboards/generate_vitals_dashboard.py`](dashboards/generate_vitals_dashboard.py)
  — edit the generator and re-run `python dashboards/generate_vitals_dashboard.py`).
- 21 panels: buzz/score e2e p50/p95/p99, DB-RPC latency by function, song-start
  latency **by `preloaded`** + stage breakdown, Realtime fan-out lag, the
  **#254 dropped-event repairs** panels (stale repairs + disconnects by
  `game_code`), Core Web Vitals p75 (LCP/INP/FCP/TTFB), active sessions,
  exceptions, and warning/error tails.

**Import:** Grafana → Dashboards → **New → Import** → upload
`sound-clash-vitals.json` → the datasources resolve by UID
(`grafanacloud-logs` / `grafanacloud-traces`) → Import. It lands with uid
`sound-clash-vitals`.

> The `game.score.e2e` panel has no data until a real game scores — there was no
> prod scoring traffic in the 2026-07-12 validation window. Its query is
> identical in shape to the validated `game.buzz.e2e` panel.

## 2. Email alert — systemic #254

- File: [`alerts/alerting-provisioning.yaml`](alerts/alerting-provisioning.yaml)
- Rule `sc_stale_buzz_lock_254`: fires when **any one `game_code` self-heals ≥3
  dropped Realtime buzz-lock events in 30 min**, evaluated every 5 min. A lone
  repair is one flaky phone; ≥3 in one game is an incident. Contact point
  `email-benartzi` → `benartzi4@gmail.com` (native Grafana Cloud email).

**Apply — pick one:**

- **UI (contact point):** Alerting → **Contact points → Add contact point** →
  name `email-benartzi`, integration **Email**, address `benartzi4@gmail.com` →
  Test (you get an email) → Save.
- **UI (rule):** Alerting → **Alert rules → New / Import** → paste the `groups:`
  block, or build by hand: datasource `grafanacloud-logs`, query
  `sum by (context_game_code) (count_over_time({service_name="sound-clash-web", kind="log"} |= "stale_buzz_lock_resynced" | logfmt [30m]))`,
  reduce **last**, threshold **IS ABOVE 2** (= ≥3), evaluate every **5m**,
  folder **Sound Clash**, `for: 0`.
- **UI (route):** Alerting → **Notification policies → New nested policy** →
  matcher `team = sound-clash` → contact point `email-benartzi`, group by
  `alertname, context_game_code`.
- **Or via the provisioning API** with an Editor SA token — see the header of
  `alerting-provisioning.yaml`.

**Validated:** the rule query evaluated at 2026-07-12 20:00 UTC returns
`3VX6QJ=3, AJJFJD=2, VHG4S4=2`, so it fires for exactly `3VX6QJ` (the real #259
dropped-frame harness incident) and not the two 2-repair games.

The second requested alert — **Realtime connections ≥150/200 + message quota** —
turned out **not directly measurable**: Supabase doesn't export a raw
connection-count or message-quota metric (those live only in the Supabase
dashboard). The Supabase Prometheus endpoint **is now scraped** into
`grafanacloud-prom` (job `supabase-soundclash`, since 2026-07-13), which instead
enables a **DB-connection-saturation** alert (Postgres `max_connections` is only
60) plus a Realtime-subscription load proxy — confirmed metrics + the buildable
alert rule are in [`supabase-metrics-scrape.md`](supabase-metrics-scrape.md).

## 3. GitHub Action — durable #254 incident record

- File: [`../.github/workflows/stale-buzz-lock-scan.yml`](../.github/workflows/stale-buzz-lock-scan.yml)
- Every 15 min it runs the same #254 query against the Loki API directly
  (read-only token), and files **one issue per incident**
  (`game_code` with ≥3 repairs in 30 min) — with occurrence timestamps,
  stale→fresh team pairs, affected `session_id`s, and a Grafana deep-link.
  Deduped by exact title (`Realtime dropped-event incident: game <CODE> (<date>)`,
  label `stale-buzz-lock`) so reruns and the overlapping cadence never
  double-file.

### Secret to set

Create a **Grafana Cloud access-policy token scoped to `logs:read`**
(grafana.com → your org → Administration → Cloud access policies → Create
access policy, realm = the `prudentcurrant2518` stack, scope **logs: Read** →
Add token) and set it as a repo secret:

```
LOKI_READ_TOKEN   =  <the access-policy token>
```

(`gh secret set LOKI_READ_TOKEN --repo BenArtzi4/Sound-Clash`)

The workflow sends it as basic auth to the stack's Loki endpoint
(`https://logs-prod-039.grafana.net`, user `1650589`, both on the
`grafanacloud-logs` datasource). The weekly `dead-video-scan.yml` reads its
in-game player failures with the same secret.

> ⚠️ **Do not route these scans through the hosted Grafana's datasource proxy**
> (`<stack>.grafana.net/api/datasources/proxy/...`). That was the original
> design, with a Viewer service-account token in `GRAFANA_READ_TOKEN`, and it
> failed almost every run from 2026-08-28 to 2026-10-09: on this free stack the
> Grafana web instance answers `503` for days at a time. The scan's own requests
> never brought it back; the success streaks each began right after a Claude
> session queried Grafana through the MCP. Loki and Grafana alerting stayed up the
> whole time (Grafana's usage-insights logs showed the `#254` alert rule
> querying Loki every 5 min in the same minutes the scan got `503`), so the
> email alert was never affected. Querying Loki directly removes the
> dependency.

### Test before trusting the schedule

Actions → **Stale buzz-lock scan → Run workflow**: `dry_run = true`, and an
`end_time` just after a known incident that is still inside Loki's retention
(14 days on the free tier). For example `end_time = 2026-10-04T21:45:03Z`
reports that it *would file* the `YQFDR6` incident (5 repairs) and prints the
full issue body, without creating anything. Then let the schedule take over.

## Visitor funnel queries

Real browsers on the live site only (a local prod-mode build reports into the
same app, and harnesses run headless):

```logql
# Where visits came from, last 7 days
sum by (event_data_ref_host, event_data_ref, event_data_src) (count_over_time(
  {service_name="sound-clash-web", kind="event"} |= "event_name=landing" | logfmt
  | page_url=~"https://(www\.)?soundclash\.org.*" | browser_userAgent!~".*Headless.*" [7d]))

# Steps of the host funnel, last 7 days (Home view → Host click → game created)
sum by (event_name, event_data_view, event_data_id) (count_over_time(
  {service_name="sound-clash-web", kind="event"} |~ "event_name=(view|cta|game_created)" | logfmt
  | page_url=~"https://(www\.)?soundclash\.org.*" | browser_userAgent!~".*Headless.*" [7d]))

# How teams joined
sum by (event_data_source) (count_over_time(
  {service_name="sound-clash-web", kind="event"} |= "event_name=team_joined" | logfmt [7d]))
```
